# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm run dev` — start dev server (`http://localhost:3000`)
- `npm run build` — production build; **use this to validate TypeScript compiles**, since `npx nuxi typecheck` is currently broken in this repo (`@nuxt/devtools` fails to dynamically import vite during `loadNuxt`)
- `npm run generate` / `npm run preview` — static generate / preview a production build locally
- `npm test` — runs the pure Vitest unit suite and the Nuxt integration suite. Use `npm run test:unit` or `npm run test:nuxt` for an individual suite. Both run with `TZ=Europe/Lisbon`; the Nuxt suite uses deterministic API fixtures under `tests/fixtures/seo-app`.

### Install quirk

Plain `npm install` fails with an ERESOLVE conflict: `@vercel/speed-insights@2.0.0` peer-depends on `vue-router@^4`, but this project uses `vue-router@^5.1.0`. If install errors on this, or `nuxt dev`/`nuxt build` errors with `Cannot find package 'vite'` (vite ends up un-hoisted in `node_modules`), run `npm install --force` — this is a known-safe workaround for an upstream peer-range lag, not a real incompatibility.

The private package `@rafaelfrancisco-dev/ipma-weather-js` is installed from GitHub Packages (see `.npmrc`); installing requires `GITHUB_PACKAGES_TOKEN` in the environment.

## Architecture

This is **MET·PT**, a Nuxt 4 / Vue 3 / Vue Router 5 app showing Portuguese weather forecasts, observations, and warnings sourced from IPMA, deployed on Vercel.

### Data layer: IPMA client via WASM

- `@rafaelfrancisco-dev/ipma-weather-js` (Rust/WASM) is the actual IPMA client. `server/utils/ipma.ts` lazily compiles the wasm module once per warm server instance and exposes cached wrapper functions (`cachedLocations`, `cachedDistricts`, `cachedWeatherTypes`, `cachedWarnings`, `cachedStations`, `cachedObservations`, `cachedForecast`) built with Nitro's `defineCachedFunction`.
- The wasm binary is **not committed**. `nuxt.config.ts` resolves it at config-eval time (plain Node, before Nitro rewrites `import.meta.resolve`) and stages it as a Nitro server asset (`useStorage('assets:ipma')`) so it ships with the deployed function.
- Type definitions for the wasm exports live in `shared/ipma-types.ts` (`JSLocation`, `JSDistrict`, `JSWeatherWarning`, `JSAggregateForecastDay`, `JSHourlyForecastPeriod`, `JSStation`, `JSStationObservation`, `JSLookupDescription`).

### Caching: two layers must stay in sync

There are two independent caching mechanisms that are intentionally tuned together — when changing one, check the other:

1. **`defineCachedFunction` maxAge** (`server/utils/ipma.ts`, `server/api/map-forecast.get.ts`) — per-function cache duration, backed by Redis in production (`nitro.storage.cache` in `nuxt.config.ts`) and filesystem in dev (`nitro.devStorage.cache`). Every cached function sets `swr: false`: Nitro's vercel preset never wires `event.context.waitUntil` to the platform, so with the default `swr: true`, an expired entry's background refresh is handed to `event.waitUntil` and dies when the serverless function freezes after responding — the entry then serves stale until the driver-level ttl evicts it (up to 25h). `swr: false` blocks on refresh instead and makes Nitro forward a per-entry `ttl: maxAge` to Redis, so each key expires on schedule; the driver-level `ttl: 90000` (25h) in `nuxt.config.ts` is now just a backstop for keys written without one (e.g. the health-check ping key). Deliberate trade-off: after expiry, an IPMA upstream failure now **throws** (500) from the cached function instead of serving eternal-stale — but every affected route sits behind an `isr` route rule, so Vercel's ISR layer serves the last successfully generated response when a background revalidation errors, and `map-forecast-batch.get.ts` already degrades gracefully per-location. This layer is unrelated to Vercel ISR cost: it's what stops every deploy-triggered ISR regeneration from hitting IPMA's real upstream API, since Redis persists across deployments while ISR's own cache does not (see below) — don't remove it as an "ISR is enough" simplification. `map-forecast.get.ts` uses a plain `defineEventHandler` wrapping its own `defineCachedFunction` rather than `defineCachedEventHandler`, because the latter derives its `cache-control` header from `opts.swr` — `swr: false` there would emit `max-age=3600` and make browsers cache the payload for 1h on top of ISR.
2. **`routeRules` ISR** (`nuxt.config.ts`) — `isr: <seconds>` per route, mapped by Nitro's vercel preset to real Vercel ISR expiration (the legacy `cache: { swr, maxAge }` shorthand does **not** work for this — it silently drops `maxAge`). ISR durations are set to roughly match the underlying data's cache maxAge so edge-served pages don't outlive the data they were built from. `/location/**`, `/api/warnings`, `/maps`, `/maps/**` are pinned to `3600` rather than something shorter: Vercel resets the entire ISR cache on every deployment, and this project deploys often, so a short window multiplies write volume fast across the ~300+ per-location paths. `/location/**`/`/maps/**` also SSR-render warnings data (banner, sidebar dots, fire-risk layer), so `cachedWarnings`' maxAge is matched to the same `3600` — warnings freshness is intentionally capped at 1h as a write-volume/freshness tradeoff. Don't shorten either side without reconsidering the other.

`cachedObservations`/`/api/observations` are the exception, running `600`/`600` rather than `3600`: station observations are the most time-sensitive data on the site and are fetched client-side only, via their own `ipma-observations` `useAsyncData` in `useLocationsData.ts` (see below), never baked into an ISR-rendered `/location/**` page, so a shorter window doesn't multiply per-deploy ISR write volume the way `/location/**`'s would. `useLocationsData()` revalidates on `visibilitychange` at two thresholds — `REVALIDATE_OBSERVATIONS_AFTER_MS` (10min, matched to the `600` above) for observations and `REVALIDATE_BOOTSTRAP_AFTER_MS` (1h, matched to warnings' `3600`) for the rest of the bootstrap — so a tab left open doesn't drift indefinitely on either axis; see the module-level `revalidationWired` guard there. Warnings freshness stays capped at 1h per the write-volume tradeoff above; don't lower `cachedObservations`/`/api/observations` without reconsidering both.

### Routing & pages

- `server/routes/index.ts` is a Nitro file route, which takes precedence over the Nuxt page renderer, so a hard load of `/` never boots Vue SSR: it reads the `metpt-last-location` cookie (`LAST_LOCATION_COOKIE` in `shared/slug.ts`), 307-redirects straight to that location (validated against `isValidLocationSlug`'s strict allowlist — the value is client-supplied and interpolated into a `Location` header) or `DEFAULT_LOCATION_PATH` (Lisboa) otherwise, and sets `Cache-Control: no-store` since the response varies per-cookie. `app/pages/location/[slug].vue` writes the cookie client-side (`import.meta.client`-gated — a server-side write would add `Set-Cookie` to ISR-cached responses) whenever the selected location changes.
- `app/pages/index.vue` only serves client-side router navigations to `/` (currently just `app/error.vue`'s `goHome()`, which also clears the cookie first so a stale cookie pointing at a removed location can't loop `/ → 404`) — it redirects to the user's last-viewed location (`useSettings().lastLocationId`), falling back to Lisboa, then the first location.
- `app/pages/location/[slug].vue` is the only real content page. The slug is `{id}-{slugified-name}` (see `shared/slug.ts`: `locationHref`/`parseLocationId`) — only the numeric id prefix is parsed/trusted; the name suffix is cosmetic/SEO only.
- `app/layouts/default.vue` is the shell: blocks render on `useLocationsData()` bootstrap, then renders `AppHeader` + `RegionTree` (sidebar) + `<main><slot /></main>`.

### Data fetching pattern

- `useLocationsData()` (`app/composables/useLocationsData.ts`) bootstraps "global" data in two separate `useAsyncData` calls sharing the same composable, deduped across components via their keys: `ipma-bootstrap` (locations, districts, warnings, weather-type descriptions, fanned out via `Promise.all` over the `/api/*` endpoints) and `ipma-observations` (stations+observations, `server: false, lazy: true` so it never blocks SSR or ships in the initial payload/hydration data — it's client-fetch-only, unlike the rest of the bootstrap). Observations were split out because they dominated the old combined payload (~87% of it) despite never being SSR-rendered; consumers read `observationsLoading` to show a loading state while the client-only fetch is in flight (e.g. `ObservationsTab.vue`).
- **`ipma-observations` needs both `dedupe: 'defer'` and its `getCachedData` — don't drop either.** Sharing a `useAsyncData` key is *not* enough to share a request when `server: false` is set. That flag puts the call on a different client init path (`nuxt/dist/app/composables/asyncData.js`): the `lazy && immediate` branch re-queues the fetch on *every* mount regardless of the entry's status, and the default `dedupe: 'cancel'` only aborts a shared `AbortController` that a plain (non-`useFetch`) handler never receives — so every caller's request really does hit the network. `useLocationsData()` runs from 3 call sites on a location page (layout, page, `useLocationForecast`) and 4 on `/maps`, which meant 3 parallel fetches of an ~850 KB payload per page view plus 2 more on every location navigation. `dedupe: 'defer'` collapses the concurrent burst onto one promise; `getCachedData` (`cachedUnlessRefreshing`) stops the refetch on later mounts. That helper's `ctx.cause` guard is load-bearing in turn: Nuxt 4 enables `experimental.granularCachedData` by default, so a custom `getCachedData` is consulted on manual refreshes too — without the guard, `refreshObservations()`/`refreshBootstrap()` would return cached data and the `visibilitychange` revalidation above would silently become a no-op.
- `useLocationForecast(id, lang, t)` (`app/composables/useLocationForecast.ts`) fetches the initial location forecast during SSR via `useAsyncData`, so ISR-cached HTML and crawlers include forecast content. Client-side navigations use a watcher that deliberately does not block Suspense or route rendering: it seeds from the SSR result when available, keeps a `useState`-backed in-memory cache (`ipma-forecast-client-cache`) keyed by location id, cancels in-flight requests via `AbortController` when the selected location changes, and guards against race conditions with a `requestId` counter.
- `usePrefetchForecast()` (same file) lets the sidebar (`RegionTree.vue`, via `@mouseenter`) start fetching a location's forecast ahead of desktop clicks, sharing the same `ipma-forecast-client-cache`. Touch navigation relies on the real navigation fetch to avoid scroll-triggered requests. Best-effort: errors are reported to Sentry but otherwise swallowed in the UI, since the real navigation fetch will retry and surface them. Two details that exist for measured reasons: the in-flight map (`inflightPrefetches`) holds the actual **promise**, and `fetchForecast` awaits an existing entry rather than issuing its own request — a click landing mid-prefetch used to fire a second identical request and wait on the slower one. It's a module-level `Map`, not `useState`, because both entry points are client-only (same guard pattern as `revalidationWired`/`nowListenersWired`) and a Promise must not land in payload-serialized, deep-reactive state; prefetch requests also deliberately carry no `AbortSignal`, so an adopting navigation can never abort a request another caller is awaiting. `RegionTree.vue` gates `prefetch` behind a ~100ms hover-intent timer cleared on `mouseleave` — without it, sweeping the cursor down the list fired a request for nearly every row it crossed. `writeForecastCache` caps the cache at 30 entries (oldest-first by `fetchedAt`) since hovering across the ~300-location sidebar would otherwise accumulate all of them.
- `pages/location/[slug].vue` renders `forecastError` + `retryForecast()` in place of `<ForecastTab>`, reusing the bootstrap-error styling from `layouts/default.vue`. Keep them wired: `ForecastTab` renders skeletons whenever its data is empty, so an unrendered error state is indistinguishable from perpetual loading (which is exactly what a failed `/api/forecast/**` used to look like).
- Client-side navigation scroll is reset in `layouts/default.vue`, not by Vue Router. `<main>` is the scroll container (`.app-shell` is `100dvh` with `overflow:hidden`), and router `scrollBehavior` only ever touches *window* scroll, which is always 0 here — so a `watch` on `route.path` sets `mainEl.scrollTop = 0`. Accepted limitation: back/forward doesn't restore the previous offset, since `savedPosition` is meaningless with an inner scroller.
- All derived/presentational data (the location tree, daily rows, hourly grid, observation grid, warning banners) is computed by pure functions in `app/utils/transform.ts` from the raw IPMA types — components themselves stay thin.

### Styling

There is no CSS framework; inline `:style`/`style` bindings remain the default for one-off component styling, using OKLCH colors (e.g. `oklch(0.975 0.004 250)`). Responsive behavior should use scoped `<style>` media queries keyed to `MOBILE_MEDIA_QUERY` in `app/utils/breakpoint.ts`: `(max-width: 700px), ((pointer: coarse) and (max-width: 1024px))`. `useViewport()` is a matchMedia-backed singleton for JS-only consumers such as map heights, `inert`, and auto-scroll; it must not gate SSR-visible layout. Color/threshold logic (temperature, precipitation, wind, UV, warning levels) is centralized in `app/utils/colors.ts`; reuse those helpers rather than inlining new color logic. `app/composables/useSettings.ts` persists user-facing theme/density/language/last-location state to `localStorage` — but it deliberately hydrates with `DEFAULTS` everywhere and only merges stored values in after hydration (`onNuxtReady`): `/location/**` pages are ISR-cached and shared, and Vue doesn't patch mismatched `:style` bindings during hydration, so any settings-dependent SSR/hydration divergence causes real breakage (a stored non-default language used to leave the language toggle visually stuck). First-time visitors default to the browser language (`pt-*` → `pt`). Never read settings-like per-user state during SSR or hydration render.

### i18n

There is no i18n module — `app/utils/i18n.ts` exports a `strings(lang)` lookup and date-formatting helpers (`weekday`, `monthShort`, etc.) for the two supported languages (`en`, `pt`), driven by `useSettings().lang`.

### SEO indexability requires `NUXT_SITE_URL`

`site.indexable` (`nuxt.config.ts`) is only `true` when `VERCEL_ENV === 'production'` **and** `NUXT_SITE_URL` is set — without `NUXT_SITE_URL` in the production Vercel env, the site ships `noindex` and broken canonical/sitemap URLs even in production. Set it to the real production URL (e.g. `https://weather-site.vercel.app`) via `vercel env add NUXT_SITE_URL production`.

Runtime OG image URLs are signed with `NUXT_OG_IMAGE_SECRET`. Configure one
stable generated value in both Vercel Preview and Production; `nuxt.config.ts`
rejects Vercel deployments where it is absent. Local commands use a local-only
fallback key so installs and builds remain self-contained.

### Error reporting: Sentry (`@sentry/nuxt`)

- Configured via `nuxt.config.ts` (`sentry: { ... }`, plus root-level `sourcemap: { client: 'hidden' }` for readable-but-unlisted client stack traces) and two root-level config files, `sentry.client.config.ts` / `sentry.server.config.ts`, each calling `Sentry.init()` directly (the DSN is a public value, hardcoded). Both capture errors and traces, sampling 100% in Preview and 10% in Production; Replay/Feedback remain disabled.
- `sentry.client.config.ts` reads `useRuntimeConfig().public.vercelEnv` rather than `process.env.VERCEL_ENV` directly — Vite doesn't expose arbitrary `process.env` vars to the client bundle, but this file runs inside a Nuxt plugin context (per the SDK), so `useRuntimeConfig()`/other Nuxt auto-imports work despite living at the repo root.
- **Server-side Sentry does not run under `nuxt dev`** — this is a documented SDK limitation (no `--import` hook in dev), not a bug. `autoInjectServerSentry: 'top-level-import'` is used instead, since Vercel's serverless runtime doesn't support the `node --import` flag; it provides the basic HTTP-level tracing used here, but not deeper database-specific instrumentation.
- Source-map upload needs `SENTRY_AUTH_TOKEN` + `SENTRY_ORG` + `SENTRY_PROJECT` in the Vercel env; without them the build just skips uploading (module warns, doesn't fail).
- Convention: catch sites that deliberately swallow errors (background revalidation, best-effort prefetch, per-location map-forecast failures) call `Sentry.captureException(error)` before falling back, so silent failures are still visible somewhere. Follow this pattern for any new best-effort catch block — don't add a truly silent `catch {}`/`.catch(() => {})`.

### Health endpoint

`server/api/health.get.ts` returns `{ ok, wasm, cache }` — `wasm` checks the IPMA wasm client can load (`isIpmaClientReady()` in `server/utils/ipma.ts`), `cache` round-trips a ping key on `useStorage('cache')`. Deliberately never calls the real IPMA upstream API, so an uptime monitor probing it doesn't consume IPMA's rate limits or reflect IPMA's own downtime as this app's downtime. `Cache-Control: no-store`. No external monitor is wired up to it yet.
